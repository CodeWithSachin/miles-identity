# Skill: scalar-api-docs

Read before adding, changing, or removing any HTTP endpoint. API documentation is not a separate task — an undocumented endpoint is an incomplete endpoint.

Verified against Better Auth 1.6.25, zod 4.4.3, Bun 1.3.x.

---

## The shape: two sources, one page

Miles Identity has two families of routes with two different owners, so the spec has two sources and Scalar merges them.

| Source | Owns | How the spec is produced |
|---|---|---|
| **Better Auth** — `/api/auth/*` | sign-in, OAuth, JWKS, OTP, SSO | generated by the `openAPI()` plugin |
| **Ours** — `/api/identity/*`, `/api/admin/*`, `/health`, `/ready` | everything we wrote | generated from the zod schemas already at each boundary |

**Do not hand-write a YAML spec.** Both halves are derived from things that already exist — the plugin's route table and our zod validators — so a hand-written spec is a third source of truth that will drift.

## Better Auth's half — the `openAPI()` plugin

```ts
import { openAPI } from "better-auth/plugins";

export const auth = betterAuth({
  plugins: [
    openAPI({
      // The bundled Scalar UI. See the production rule below before enabling.
      disableDefaultReference: config.NODE_ENV === "production",
    }),
    // …existing plugins
  ],
});
```

- Serves a Scalar reference at **`/api/auth/reference`** by default.
- `auth.api.generateOpenAPISchema()` returns the spec as a JSON object — this is what we serve to our own Scalar page.
- Raw schema endpoint: `/api/auth/open-api/generate-schema`.
- OpenAPI **3.1.1**. If you point a client generator at it, confirm the generator speaks 3.1, not just 3.0.
- The plugin is described upstream as early-stage. Expect gaps; do not assume every plugin route is described.

## Our half — from zod, natively

`zod@4` has `z.toJSONSchema()` built in. **Do not add `@asteasolutions/zod-to-openapi`, `zod-openapi`, or similar** — there is nothing to install.

```ts
import { z } from "zod";

export const ResolveIdentityBody = z.object({ handle: z.string().min(1) });

// → { type: "object", properties: { handle: { type: "string", minLength: 1 } }, … }
const schema = z.toJSONSchema(ResolveIdentityBody);
```

Rules:

- The zod schema that **validates** a request is the same object the spec is generated from. One definition, two uses. If they diverge, the docs are lying.
- Response schemas get the same treatment. A documented response shape that nobody validates is a guess.
- JSON Schema draft 2020-12 is what zod emits, which is what OpenAPI 3.1 uses. No conversion layer.

## Serving it — Bun-native

No Express, no Hono, no `@scalar/express-api-reference`. `Bun.serve` static routes plus the Scalar CDN script:

```ts
// src/routes/docs.ts
export const openApiSpec = (spec: object) =>
  Response.json(spec, { headers: { "cache-control": "no-store" } });

export const scalarPage = new Response(
  `<!doctype html><html><head><title>Miles Identity API</title>
   <meta charset="utf-8"><meta name="viewport" content="width=device-width,initial-scale=1"></head>
   <body><div id="app"></div>
   <script src="https://cdn.jsdelivr.net/npm/@scalar/api-reference"></script>
   <script>
     Scalar.createApiReference('#app', {
       sources: [
         { url: '/api/docs/openapi.json', title: 'Identity API' },
         { url: '/api/auth/open-api/generate-schema', title: 'Auth' },
       ],
     })
   </script></body></html>`,
  { headers: { "content-type": "text/html; charset=utf-8" } },
);
```

A static `Response` in `routes` is dispatched with zero allocation, which is the right call for a page that never changes.

## Security — the part that matters

An API reference with a "Try it" console, mounted on an identity provider, is an attack surface. Treat it as one.

**1. Never expose the reference or the spec publicly in production.** Pick one and state which in the plan:

- not mounted at all when `NODE_ENV === "production"` (simplest, recommended);
- or mounted behind an authenticated admin check.

There is no third option. `disableDefaultReference: true` in production, and our `/api/docs/*` routes registered conditionally.

**2. Never document `/api/internal/*`.** Salesforce provisioning, vendor domain verification and friends are network-allowlisted and signed. Publishing their shapes hands an attacker the map. Exclude them explicitly rather than relying on nobody noticing.

**3. No real secrets in examples.** No live client secret, no real `BETTER_AUTH_SECRET`, no working token, no real phone number or email. Obvious, and it still happens — examples get copy-pasted from a terminal.

**4. Do not document the enumeration distinction.** `/api/identity/resolve` deliberately returns an identical shape and timing for hit and miss. The spec must describe **one** response, not "200 when the handle exists, 404 when it does not". A spec that documents a difference the code does not have is a disclosure in its own right.

**5. Never let the spec become the authorization story.** Documenting that a route requires `ADMIN` does not enforce it. The handler still needs its explicit check.

**6. CSP.** If a CSP is added later, the Scalar inline script needs a nonce — the `openAPI()` plugin accepts a `nonce` option for exactly this.

## Documentation is part of "done"

For every endpoint added or changed, the plan must state:

- the zod schemas for request and response, and that the spec derives from them;
- the auth requirement, and which scheme it maps to;
- whether the route is public, admin-only, or internal-and-therefore-undocumented;
- the error responses, described honestly — including the deliberately-indistinct ones.

And the acceptance criteria must include the route appearing correctly in the reference. "Documented" means visible and accurate in Scalar, not "a comment was added".

## Verification

```bash
bun run dev

# spec is valid JSON and contains the new route
curl -s localhost:3000/api/docs/openapi.json | jq '.paths | keys'

# internal routes are absent — this must print 0
curl -s localhost:3000/api/docs/openapi.json | grep -c '/api/internal'

# Better Auth's half resolves
curl -s localhost:3000/api/auth/open-api/generate-schema | jq '.info.title'

# the reference renders
open http://localhost:3000/api/docs

# production posture: with NODE_ENV=production both must 404
NODE_ENV=production bun src/index.ts &
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/api/docs           # → 404
curl -s -o /dev/null -w '%{http_code}\n' localhost:3000/api/auth/reference  # → 404
```

The last two are the security assertions. Run them by hand at least once, and keep them as tests.

## Do not use

| Instead of | Use |
|---|---|
| Swagger UI, Redoc, RapiDoc | Scalar |
| `@scalar/express-api-reference`, Hono middleware | `Bun.serve` static route + CDN script |
| `@asteasolutions/zod-to-openapi`, `zod-openapi` | `z.toJSONSchema()` — zod 4 native |
| A hand-written `openapi.yaml` | generated from zod + the `openAPI()` plugin |
| `swagger-jsdoc`, JSDoc annotations | the zod schema at the boundary |
