# 009 — Masterclass web OIDC integration + flagged legacy password login

---

## Goal

Give Masterclass web a real, Masterclass-themed hosted login page against the already-registered `masterclass-web` OAuth client, and let existing (not-yet-otherwise-migrated) Masterclass users sign in with their legacy Django password via an imported (never proxied) hash, gated by a flag that defaults off.

  - `src/db/migrations/0002_user_identity.sql`: `user_identity` requires `is_verified`+`verified_at` together, `source IN (..., 'masterclass', ...)`, and a global `UNIQUE (type, value)` — an import must go through the same writer path as everything else, not a one-off `INSERT`.

## Assumptions

1. **Legacy source is Postgres.** `LEGACY_MASTERCLASS_DATABASE_URL` isn't schema-validated to a scheme in `config.ts` (unlike `DATABASE_URL`), so this is a real unknown. Assuming Postgres, reachable via a second `Bun.SQL` instance per `bun-native.md`. **Must be confirmed against the real Masterclass DB before this runs anywhere but a local/staging copy** — if it turns out to be MySQL, the reader in `src/integrations/legacy-masterclass-db.ts` is the only file that changes.
2. **Legacy schema is Django's default `auth_user`** (`id`, `email`, `password`, `is_active` at minimum) — Masterclass's backend is Django per `docs/architecture-plan.md:15`, and no custom user model is mentioned for Masterclass (only Miles One's `AUTH_USER_MODEL` migration is called out, at a later step). If Masterclass uses a custom user model or a different table name, the reader query is the only place that changes.
3. **Imported identities are marked verified**, not `invited`/unverified like Salesforce provisioning (AGENTS.md security rule 11 is about *new* Salesforce leads, a different case). These are real, already-active Masterclass accounts being migrated wholesale, not self-service claims — `is_verified = true`, `source = 'masterclass'`, `verified_at = now()` at import time. **Confirm this reading is correct** — if wrong, these users get `is_verified = false` and must go through OTP verification once, which changes the whole point of importing the hash.
4. **One user per legacy row, matched by normalised email.** If a `user_identity` row already exists for that email (globally unique), the import **skips** that row rather than erroring or merging — cross-system dedup is step 10's job, not this one. Anyone already known to Miles Identity is left alone.
5. **Scope is Masterclass only.** LMS and Miles One legacy import stays step 10/13 as ordered; this task does not touch `LEGACY_LMS_DATABASE_URL` or `LEGACY_MILES_ONE_DATABASE_URL`.
6. **The flag (`MASTERCLASS_LEGACY_PASSWORD_LOGIN_ENABLED`) gates password sign-in for imported-but-not-yet-rehashed accounts only**, confirmed with the user. Default `false` (fail closed): an imported user cannot sign in with their legacy password until this is turned on, and can always fall back to email/SMS OTP (already live, step 5) regardless of the flag. Once a password sign-in succeeds once, the hash rehashes to argon2id and the account is no longer gated by this flag at all.
7. **Hosted login page is a single static page, one theme, no per-`client_id` theme registry.** Masterclass is the first and only product wired to a real login page — building a theme-lookup system for clients that don't exist yet is speculative. The page hard-codes Masterclass branding (logo URL, primary colour from a small constants object) so a second product's theme is a follow-up, not a system built now on guessed requirements.
8. **The login page is plain HTML/CSS/vanilla JS**, served as a static-ish `Response` the same way `src/routes/docs.ts` serves the Scalar page — no bundler, no framework, matching the "no dependency for what native features cover" rule. It calls the existing `/api/identity/resolve`, `/api/auth/sign-in/email`, and `/api/auth/sign-in/otp/start|verify` endpoints; it adds no new JSON API of its own.
9. **No consent page is built.** `masterclass-web` has `skipConsent: true` (already seeded), so `/consent` is never reached for this client. Building it now would be speculative for a screen no traffic can hit.

## Implementation requirements

1. **`src/lib/pbkdf2.ts`**
   - `verifyDjangoPbkdf2(password: string, encoded: string): Promise<boolean>`.
   - Split on `$`; reject (return `false`, never throw) if the format doesn't have exactly 4 parts or doesn't start with `pbkdf2_sha256`.
   - `crypto.pbkdf2Sync(password, salt, Number(iterations), 32, "sha256")`, base64-encode, compare against the decoded expected hash with `crypto.timingSafeEqual` (equal-length buffers only — different lengths return `false`, not a thrown error).

2. **`src/lib/config.ts`**
   - `MASTERCLASS_LEGACY_PASSWORD_LOGIN_ENABLED: z.enum(["true","false"]).transform(v => v === "true").default(false)` — same shape as `DEV_OTP_BYPASS`. No production restriction (unlike `DEV_OTP_BYPASS`, enabling this in production is the whole point of the rollout), but it defaults closed.

3. **`src/auth.ts`**
   - `passwordHasher.verify`: `if (hash.startsWith("pbkdf2_sha256$")) return verifyDjangoPbkdf2(password, hash); return Bun.password.verify(password, hash);` (exact branch named in `better-auth.md`).
   - `user.additionalFields.importedHashAlgo: { type: "string", required: false, input: false, fieldName: "imported_hash_algo" }`.
   - `hooks.before`: matcher on the sign-in/email path; look up the target account's `importedHashAlgo` (via a lazily-imported helper, same `getAccessTokenClaimsBuilder`-style seam used elsewhere for CLI/jiti compatibility); if it is set **and** `config.MASTERCLASS_LEGACY_PASSWORD_LOGIN_ENABLED` is `false`, return the same generic invalid-credentials shape Better Auth already returns for a wrong password — no distinct error, no distinct timing (security rule: hit/miss must be indistinguishable).
   - `hooks.after`: on a successful sign-in/email response, if the account's `importedHashAlgo` is set, rehash the plaintext password (available in the request body at this hook point) to `Bun.password.hash`, update the account's password via the adapter, and clear `importedHashAlgo` to `null`. Never touch this on a failed sign-in.

4. **`src/integrations/legacy-masterclass-db.ts`**
   - `const legacyDb = new SQL(config.LEGACY_MASTERCLASS_DATABASE_URL)` created lazily (same jiti/CLI-safety reasoning as `getRedis`).
   - `fetchLegacyMasterclassAccounts(): Promise<{ email: string; password: string; isActive: boolean }[]>` — `SELECT email, password, is_active FROM auth_user`. Parameterised, no dynamic identifiers.

5. **`src/db/identity.ts`**
   - `createVerifiedIdentity({ userId, type, value, source }, client = sql)`: `INSERT INTO user_identity (id, user_id, type, value, is_primary, is_verified, source, verified_at) VALUES (${newId("identity")}, ${userId}, ${type}, ${value}, true, true, ${source}, now()) ON CONFLICT (type, value) DO NOTHING RETURNING *`. Returns `null` on conflict — the caller treats that as "already known, skip."

6. **`src/services/legacy-import.ts`**
   - For each legacy row: skip if `!isActive` or the email fails `normaliseHandle`/basic validation.
   - Call `createVerifiedIdentity` first (cheapest existence check, respects the global unique constraint) — if it returns `null`, skip the row entirely (no user/account created; someone already owns this email).
   - Otherwise create the `user` row and a `credential`-provider `account` row with `password: legacyRow.password` (the raw Django hash string, untouched) and `importedHashAlgo: "django_pbkdf2"`, via `auth.$context.adapter.create`, then attach the just-created `user_identity` row's `user_id`.
   - Log one structured line per outcome (`imported` / `skipped_existing` / `skipped_inactive`) with counts only — no email addresses, no hashes, no passwords (security rule: never log a hash).
   - `import.meta.main` CLI entrypoint mirroring `seed-oauth-clients.ts`, printing a summary count.

7. **`src/routes/login.ts`**
   - `signInPage: Response` — static HTML/CSS/inline vanilla JS. Fields: handle input → `POST /api/identity/resolve` to learn available methods → password field (if eligible) or "send code" flow reusing `/sign-in/otp/start` + `/sign-in/otp/verify`. Masterclass logo/colour hard-coded per assumption 7. `Cache-Control: no-store` (an auth page must never be cached).

## Data model impact

- New Better-Auth `user` additional field: `imported_hash_algo` (nullable text, `input: false`). Generated by `bunx @better-auth/cli generate` (review the diff before applying), applied with `bun run auth:migrate` — **no hand-written migration file**, matching how `salesforceContactId`/`status`/`mergedIntoUserId` were added.
- No changes to `user_identity`, `user_product_access`, or any other table we own. `createVerifiedIdentity` reuses the existing schema and its constraints (`uq_identity_value`, the verified/verified_at pairing check) as-is.
- Save rules enforced: the global `UNIQUE (type, value)` in the schema is what makes the "skip if already known" behaviour correct even under a concurrent run — not an app-level check alone.

## Security requirements

- **Never proxies to the legacy database at login time** — the explicit thing `docs/architecture-plan.md` rejects. The legacy DB is read exactly once, by the offline import job, never from a request handler.
- **Fails closed by default.** `MASTERCLASS_LEGACY_PASSWORD_LOGIN_ENABLED` defaults `false`; an imported user cannot password-login until this is explicitly turned on, and can always use OTP regardless.
- **Takeover path 1 (unverified alias can log in):** imported identities are marked verified per assumption 3 — flagged for explicit confirmation since it's a deliberate, non-default reading of that rule. The negative test is: an email that already exists as a `user_identity` row is **never** re-created or re-verified by the import (assumption 4), so the import cannot be used to silently "verify" a handle someone else already claimed.
- **Enumeration:** the sign-in page's own calls are all to already enumeration-safe endpoints (`/api/identity/resolve`); no new endpoint is added that could differentiate existence. The `hooks.before` rejection for a flag-gated imported account returns the *same* generic invalid-credentials shape as a wrong password — it must not be a distinct error code or message.
- **Timing:** `verifyDjangoPbkdf2` uses `timingSafeEqual`, not `===`, for the hash comparison.
- **Never logged:** the import job logs counts and outcomes only, never an email, hash, or password (security rule 10).
- **Rehash-on-login only follows a verified success** — never on a failed or rejected attempt, and never from anywhere but the `hooks.after` seam on the real sign-in flow.
- **No new secret.** `LEGACY_MASTERCLASS_DATABASE_URL` already exists in tier 2 and already flows through `lib/config.ts` only.

## Authorization impact

None. This is authentication-only; no `user_product_access` row is created or read by the import (a migrated user's product access, if any, is step 10/13's dedup+RBAC-backfill concern, not this one — an imported user gets no product access here and must be granted it separately, consistent with "smallest, reversible" framing).

## Bun-native check

- New dependencies: **none**. `node:crypto`'s `pbkdf2Sync`/`timingSafeEqual` are Bun-bundled Node-compat builtins (not an npm package), matching `bun-native.md`'s own Django-PBKDF2 pointer. The legacy DB reader uses a second explicit `Bun.SQL`/`SQL` instance, exactly as `bun-native.md` recommends for "the legacy source DB." No ORM, no ID/crypto/HTTP library added.

## Acceptance criteria

- [ ] `masterclass-web`'s existing OAuth client redirects a browser through `/sign-in`, which renders a Masterclass-branded page (not the default Better Auth behaviour of nothing being served).
- [ ] Running the import job against a legacy `auth_user` table with an active row creates exactly one `user` + verified `user_identity` (`source='masterclass'`) + `account` row with `imported_hash_algo='django_pbkdf2'`.
- [ ] Re-running the import job is a no-op for rows already imported (or already known via any other source).
- [ ] With the flag off, a freshly-imported user's password sign-in is rejected (generic invalid-credentials response) but their email/SMS OTP sign-in still works.
- [ ] With the flag on, the same user's correct legacy password succeeds, and their `account.password` is now an argon2id hash with `imported_hash_algo` cleared — a second sign-in succeeds via `Bun.password.verify` alone, regardless of the flag.
- [ ] An inactive legacy row (`is_active=false`) is never imported.

## How to verify it

```bash
1. bun run check
   → typecheck clean, all tests green (including the new legacy-login negative tests), audit clean

2. bunx @better-auth/cli generate   # review the diff: only imported_hash_algo added to user
   bun run auth:migrate

3. curl -i http://localhost:3000/sign-in
   → 200, content-type: text/html, cache-control: no-store, body contains Masterclass branding

4. Seed one row into a local legacy Postgres DB with a real Django pbkdf2_sha256 hash,
   set LEGACY_MASTERCLASS_DATABASE_URL to it, then:
   bun run masterclass:legacy-import
   → "imported 1" — a user_identity row exists, is_verified=true, source='masterclass'

5. Security property — flag off:
   curl -X POST localhost:3000/api/auth/sign-in/email -d '{"email":"<imported>","password":"<real legacy password>"}'
   → generic invalid-credentials response (NOT a 200), identical shape to a wrong password

6. Set MASTERCLASS_LEGACY_PASSWORD_LOGIN_ENABLED=true, restart, repeat step 5's curl
   → 200 with a session; inspect the account row → password is now an argon2id hash,
     imported_hash_algo is NULL

7. Repeat step 5's curl again (same credentials, flag can be true or false now)
   → still 200 — Bun.password.verify alone now handles it, no PBKDF2 branch involved
```
